# Create And Maintain Isostate Assets

Deliver reusable artwork with checked geometry, stable identifiers, accurate
catalog metadata, and reproducible distribution. The user supplies the visual
style; this skill supplies the isostate technical contract.

## Start With The User's Style

Capture the requested medium, reference images or existing catalog, palette,
materials, perspective, lighting, detail, and intended viewing size. Use what
the user already supplied. Inspect reference artwork before extending it.
For an existing catalog, “keep our style” means match that catalog.

For a new family with no style direction or reference, ask one focused question
about the desired style. Inventory concepts and inspect integration paths while
waiting; do not generate artwork in an invented default style. Flat vector,
watercolor, pixel art, clay, and photorealistic designs are all valid choices.
Do not substitute simple boxes for a requested detailed material treatment.

Define each logical object's role and requested variants before production.
Distinguish semantic variants such as human-to-human, human-to-AI, AI-to-human,
or active/idle states. A recognizable asset must support its actual label.

## Choose The Work

- **Create or restyle:** read [generation.md](references/generation.md) for
  style-aware prompts, tool selection, and source/provenance records.
- **Import, crop, or repair:** read [geometry.md](references/geometry.md) for
  supported formats, sprite rectangles, viewport anchors, and rendered checks.
- **Add, replace, rename, or distribute:** read
  [catalog-lifecycle.md](references/catalog-lifecycle.md) for metadata, CLI
  commands, stable IDs, notices, and source/build/website synchronization.

Read only the references for the operation being performed. In the isostate
repository, verify current contracts in `specs/01-domains/assets.md`,
`specs/03-contracts/asset-manifest.md`, and the scene schema before modifying
technical behavior. Installed copies carry the baseline details in these
references; prefer the target project's newer documented contract when present.

## Essential Requirements

- Keep artwork pre-rendered in 2D. The browser uses SVG plus diamond projection;
  asset creation must not add a 3D engine, image-generation service, or parsing
  dependency to playback.
- Choose one logical concept per placeable asset. Give independently positioned
  concepts their own assets. Keep tightly composed concepts together only when
  they are deliberately authored and checked for one native cell.
- Declare imported art at native `size: 1` with a checked viewport anchor. Do not
  enlarge a composite to compensate for incorrect crops or empty source space.
- Standalone URL assets are SVG. Raster images, including a single full-image
  object, use `type: sprite-sheet` with exact dimensions and explicit metadata.
  Sheet IDs are namespaces; scene elements place nested sprite IDs.
- Preserve original generated bytes as source. Cropping through sprite `rect`
  metadata changes the viewport, not the pixels. Keep derived exports separate
  when the user requests image transformations or optimization.
- Keep text labels and long connectors outside object artwork. Author `text`
  elements and scene `connections` for them. Respect requested identifying
  detail while keeping domain labels editable and legible.
- Use unique, stable IDs and keep source ownership/licence records per family.
  Disclose the actual generation provider; never invent a model ID or apply an
  AI credit to imported third-party artwork.

## Verify And Finish

Generate the catalog through the CLI and validate a scene that actually uses the
changed objects. Compile changed scene sources and regenerate their bundles.
For maintenance-only changes, inspect existing artwork; generate new images
only when that is part of the requested operation.

Inspect the rendered result on the backgrounds, desktop/mobile sizes, and scene
stops used by the product. Check ground contact, crop clipping, neighboring
sprites, actual label size, caption/artwork collisions, and semantic variants.
Passing metadata validation alone does not establish visual quality. For a
standalone verification scene and browser host, read
[preview.md](references/preview.md).

Report the user style used, changed assets/IDs, source and derived files,
validation and rendered evidence, and any remaining blocker. Do not claim a
catalog is ready when it contains clipped objects, fake transparency, ambiguous
variants, orphaned metadata, stale copied files, or missing licence/provenance.
If the required image tool or a source permission is missing, identify the
specific limitation and continue independent metadata/documentation work.
